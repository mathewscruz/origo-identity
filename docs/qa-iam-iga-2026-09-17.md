# QA profundo — lógica IAM/IGA do Órigo Access & Identity

**Data:** 2026-09-17 · **Escopo:** 24 edge functions (~9.8k linhas), funções/triggers/RLS do banco, libs do frontend (`src/lib`, hooks), agente Python, MCP. Cada achado marca o arquivo. Itens marcados **[verificado]** foram reproduzidos no ambiente local.

## 0. Resumo executivo

O sistema tem todas as peças de um IGA (JML, RBAC por cargo, solicitações com workflow, revisões, SoD, exceções, privilegiados, auditoria), mas **vários controles centrais não fecham de ponta a ponta** e há funcionalidades quebradas em produção:

| # | Achado | Impacto |
|---|--------|---------|
| C1 | `start-jml-event` não sobe (erro de sintaxe) | Iniciar JML via MCP/agente ou pelo diálogo retorna 503 |
| C2 | Tool MCP `approve_iam_item` faz PATCH em colunas inexistentes | Hermes nunca consegue aprovar/cancelar itens |
| C3 | Expiração de contrato de terceiro só muda flags no banco | Terceiro expirado continua com conta e acessos ativos |
| C4 | Leaver por ausência no CSV **apaga** o colaborador e o histórico; reconciliação apaga "fantasmas" | Trilha de offboarding destruída; risco de offboarding em massa por CSV parcial |
| C5 | Leaver vindo do RH não remove grupos/licenças/apps do cargo | Só desabilita a conta; licenças continuam (custo) e acessos voltam se reabilitar |
| C6 | No modo `agent_orchestrated`, `enable_entra` sempre falha e AD `update` não é suportado | Reativação/retorno de férias/reversão de pré-leaver nunca reabilita conta |
| C7 | Fila sem reserva atômica nem máquina de estados; qualquer operador altera status | Execução duplicada; aprovação não é um controle real |
| C8 | Remoções ignoram acesso efetivo (outro perfil ainda concede) | Revoga acesso legítimo; `remove_license` herdada tira o usuário do grupo inteiro |
| C9 | Mover nunca remove acesso do cargo anterior (por design) | Acúmulo de privilégios — contraria least privilege |
| C10 | SharePoint enfileirado como `assign_app` sem `appId`; `assign_sharepoint` sem implementação no Lovable | Provisionamento SharePoint só funciona se o agente executar |

Além disso: **nada roda sozinho** (o ciclo diário exige JWT humano e não há cron nas migrations), o motor de regras está morto, e a lógica JML roda no navegador sem transação.

## 1. Como o sistema funciona hoje (mapa)

```
RH (CSV no SharePoint) ─► sync-sharepoint-csv ─┐
Upload manual CSV ──────► sync-csv-colab ──────┤ (cópias divergentes)
                                               ▼
                                  colaboradores / perfil_atribuicoes
                                               │
Operador (browser) ── colaboradorLifecycle.ts, preLeaver.ts, entraQueueHelper.ts,
                      provisionCargoAcessos.ts, workflow/engine.ts ──┐
Portal (solicitações) ── workflow/engine.ts → provisioning.ts ───────┤
Revisões / exceções ── save-external-review, expire-access-exceptions ┤
                                                                      ▼
                                                            iam_queue (fila + "ledger")
                                                                      │
              ┌───────────────────────────────────────────────────────┤
              ▼                                                       ▼
   process-iam-queue (Graph + apps externos)              iam-agent-api /pending → Órigo/Hermes agent
   (modo lovable_cloud; em agent_orchestrated só delega)  (AD via LDAP/bridge, Entra, SharePoint)
```

- **AD local** (`create`, `create_if_not_exists`, `update`, `disable`): só o agente executa.
- **GLPI**: não existe integração neste repositório. GLPI aparece apenas como exemplo de conector de aplicação externa (`AplicacaoDetalhePage`, auth `app_token`). A leitura de chamados acontece fora (no Hermes), que entra no Órigo pelo MCP — **fora do workflow de aprovação** do produto.
- **Aprovação**: trigger `iam_queue_apply_approval_gate` converte `pending`→`waiting_approval` quando `parametros.iam_approval_required = true`. A "aprovação" é um `UPDATE status='pending'` que qualquer `operador` pode fazer.

## 2. Achados críticos

### C1. `start-jml-event` está quebrado **[verificado]**
`supabase/functions/start-jml-event/index.ts:37` e `:46` declaram `allowed` duas vezes no mesmo escopo → `SyntaxError: Identifier 'allowed' has already been declared` → worker não sobe (HTTP 503 `BOOT_ERROR`). Afeta `StartJmlEventDialog` e a tool MCP `start_jml_event`.
Além do erro: a função **só grava o registro** em `eventos_jml` (status `executando`/`pendente`) — não enfileira nenhuma ação. Um JML iniciado pelo agente não provisiona/revoga nada; o evento fica "executando" para sempre.

### C2. Tool MCP `approve_iam_item` está quebrada **[verificado]**
`src/lib/mcp/tools/approve-iam-item.ts:21-25` envia `updated_at` e `last_error`, colunas que não existem em `iam_queue` → PostgREST `PGRST204`. Também não preenche `approved_by`/`approved_at` (que existem).

### C3. Expiração de terceiro não revoga nada
`supabase/functions/auto-recertification/index.ts:222-262`: `terceiros.ativo=false`, `perfil_atribuicoes.ativo=false`, evento leaver e alerta "Acessos revogados automaticamente" — **nenhum item em `iam_queue`** (`disable_entra`, `disable`, `remove_*`). Contraste com `desligarTerceiro` (frontend), que enfileira tudo.

### C4. Leavers do CSV destroem histórico / risco de offboarding em massa
- `sync-csv-colab/index.ts:849-856`: matrícula ausente do arquivo ⇒ `DELETE` de `perfil_atribuicoes`, `excecoes`, `revisao_itens` e **`colaboradores`** (e `eventos_jml` por `ON DELETE CASCADE`). O evento leaver é gravado com `colaborador_nome = matrícula` e sem `colaborador_id`.
- `sync-sharepoint-csv/index.ts:706-715` já foi corrigido para marcar `desligado` (comentário "Preserve IAM history") — as duas funções divergiram.
- **Nenhuma das duas tem limite de segurança**: um CSV parcial/truncado ou com coluna renomeada desliga (ou apaga) todo mundo que faltar. As tabelas `backup_colaboradores_restore_20260707` indicam que isso já aconteceu.
- `reconcile-identities/index.ts:160-198, 572-587`: "phantom leavers" (desligados/inativos de origem CSV sem conta correspondente no Entra) são **apagados** com todo o histórico. Todo ex-colaborador cuja conta foi removida do Entra após o offboarding vira "fantasma" e some do IAM no ciclo seguinte — perde-se a evidência de offboarding.

### C5. Leaver do RH não remove acessos do cargo
`sync-csv-colab/index.ts:867-871` e `:1002-1008` chamam `provisionCargoAcessosServer(sb, id, null, oldCargo, …)`; a função (`:238-283`) só revoga no banco quando `newCargoId` é nulo — nunca enfileira `remove_*` (o próprio comentário diz "DB only — no Entra removal"). Só perfis de origem ≠ cargo geram remoção. Resultado: conta desabilitada, mas grupos/licenças/apps permanecem. Mesmo comportamento em `sync-sharepoint-csv`.

### C6. Agente: reativações nunca acontecem; AD `update` não suportado
- `agent/origo_iam_agent_executor.py:157-165`: `has_approval` exige `payload_json.approved_by` ou `evento_jml_id` — **nenhum produtor preenche isso** (a aprovação grava a coluna `approved_by`). `enable_entra` sempre retorna `missing_approval` (não retentável → `failed`). Afeta reativação, retorno de férias/afastamento, reversão de pré-leaver e divergências `reconcile-status`.
- `:202-204`: via LDAP, só `create`/`create_if_not_exists`/`disable`; `update` (reabilitar conta AD, mudança de título/departamento) → `unsupported_ad_action`. `delete` (exposto em `iam-agent-api` `AD_LOCAL_ACTION_TYPES`) não existe no agente.
- `:356-360`: identidade resolvida só por `payload.mail/samAccountName`. Itens sem isso no payload falham com `user_not_found`: solicitações do portal (`src/lib/workflow/provisioning.ts:39-43`), remoções de `reconcile-identities` (`:349,:373`), aprovação de órfãos (`AprovacaoIAMPage.tsx` usa `entra_id`, que o agente ignora).
- `disable_entra` (`:373-377`) não chama `revokeSignInSessions` — o pré-leaver promete isso no payload (`preLeaver.ts:85`) e ninguém executa (nem `process-iam-queue`).

### C7. Fila sem reserva, sem máquina de estados, aprovação sem enforcement
- `iam-agent-api/index.ts:111-118`: `GET /pending` devolve os 10 mais antigos **sem marcar** como `processing`. Dois pollers, ou um poll mais rápido que a execução, executam o mesmo item duas vezes. As funções `claim_iam_queue_items`/`complete_iam_queue_item` existem no banco e não são usadas.
- `:199-214`: `POST /update` aceita qualquer `status` para qualquer item (inclusive `waiting_approval` → `success` sem executar). Sem validação de transição.
- `process-iam-queue/index.ts:1536`: `select` → `update processing` não atômico; a UI chama a função após cada ação (`triggerEntraProcessing`) e o ciclo diário também → concorrência real.
- RLS: `admin` e `operador` têm INSERT/UPDATE em `iam_queue`, `perfil_atribuicoes`, `excecoes`, `parametros`, `workflow_execucoes` e **`auditoria`** (UPDATE; admin DELETE). Aprovar = `UPDATE status`. Anti-auto-aprovação existe só no cliente (`workflow/engine.ts:142`). O trigger de gate só intercepta INSERT com `pending`; `useReprocessQueueItem` zera retries e volta para `pending` sem passar pelo gate.
- Vocabulário de status sem CHECK: `pending, waiting_approval, processing, success, failed, cancelled, rejected`; `permanent_failure` é lido (`useQueueActions.ts:60`) mas nunca gerado.

### C8. Remoções sem cálculo de acesso efetivo
Não existe "quem tem o quê" consolidado; `iam_queue` faz de ledger (`sync-user-access` grava linhas `success`/`entra_sync`). Consequências:
- `expire-access-exceptions/index.ts:57-109`, `usePerfilAssignment.ts:77`, `save-external-review/index.ts:105-161`, `terceiroLifecycle.ts:77`: remover um perfil remove **todos** os recursos dele, mesmo os ainda concedidos por outro perfil ativo (ex.: birthright do cargo).
- `process-iam-queue/index.ts:263-292`: `remove_license` herdada de grupo **remove o usuário do grupo** que atribui a licença — e com ele tudo o que o grupo concede.
- `colaboradorLifecycle.ts:220-261` reconstrói "recursos individuais" a partir do histórico de sucessos da fila.

### C9. Mover não remove nada (acúmulo)
`provisionCargoAcessos.ts:65-77` ("Never remove on cargo change"), `entraQueueHelper.ts:393-406`, `provisionCargoAcessosServer`. Mudança de cargo só adiciona. Contraria least privilege; combinado com C8, não há caminho seguro para remover.

### C10. SharePoint
`entraQueueHelper.ts:204-246` enfileira SharePoint como `assign_app`/`remove_app` com `resourceType: "sharepoint"` e sem `appId` → `process-iam-queue` responde "appId ausente" (10 retries, `failed`, alerta). Os tipos `assign_sharepoint`/`remove_sharepoint` estão em `ENTRA_ACTION_TYPES` mas `executeAction` não os implementa. `provisionCargoAcessos.ts` ignora `sharepointItems` no delta. Só o agente (`:534-…`) trata SharePoint.

## 3. Achados altos

**A1. Override manual vira exceção de 1 ano.** `colaboradorLifecycle.ts:78-107`: toda mudança manual de status insere `excecoes` aprovada por 1 ano (`manter_ativo` ao reativar). Reativar alguém por engano bloqueia o leaver do RH por um ano (`handleStatusChange:46-61`, `sync-sharepoint-csv:601-616`). `sync-csv-colab` **ignora** esses overrides (usa só `desligado_manual`). A tabela de exceções (controle IGA) fica poluída com registros automáticos.

**A2. Lógica JML no navegador, sem transação.** `handleStatusChange` faz ~15 escritas sequenciais com o JWT do operador; fechar a aba no meio deixa estado parcial (status alterado, perfis revogados, nada enfileirado). Idem `preLeaver.ts`, `terceiroLifecycle.ts`, `workflow/engine.ts` (aprovação inteira no browser do aprovador).

**A3. Duplicação com divergência.**
- `sync-csv-colab` × `sync-sharepoint-csv` (1.2k + 1k linhas, "inlined because Edge Functions can't share code" — mas `_shared/` já existe). Divergem em: delete × desligado, honrar overrides, vínculo com colaboradores manuais, dedupe.
- `provisionCargoAcessos.ts` (cliente) × `provisionCargoAcessosServer` (servidor): o servidor não grava `colaborador_id` nos itens (`queueProfileAccess`), usa `target_identity = sam`, ignora SharePoint e flag on-prem.
- Reconciliação em `process-iam-queue` (modo `reconcile-create`, ~600 linhas) × `reconcile-identities` (912 linhas): duas engines de matching, duas listas de cancelamento/linkagem.

**A4. Nada roda sozinho.** `run-daily-cycle` exige JWT de admin/operador humano (`requireRole`) e repassa esse JWT às sub-funções; `auto-recertification`, `expire-access-exceptions`, `execute-rules`, `audit-reconciliation` não são chamadas por nenhuma tela; as migrations removeram os `cron.schedule`. **Verificar em produção:** `select jobname, schedule, command, active from cron.job;`. Se estiver vazio, revisões automáticas, expiração de exceções/terceiros e o ciclo do RH dependem de alguém clicar.

**A5. Privilégios administrativos.**
- `admin_exec_sql`/`admin_exec_ddl` (SECURITY DEFINER, bypass RLS): qualquer usuário com papel `admin` do app executa DDL/DML arbitrário via RPC/MCP, inclusive `DELETE FROM auditoria`. Um administrador de IAM não deveria ter poder de alterar a trilha.
- `reset-entra-password/index.ts:136-150`: `operador` reseta senha de qualquer conta (inclusive privilegiadas), a senha temporária volta para o navegador e a auditoria registra `operador: "sistema"` (sem ator).
- `parametros` editável por `operador`: desliga `iam_approval_required`, muda `modo_operacao`/`iam_execution_mode`.
- O agente (IA) pode **aprovar** itens via MCP (`approve_iam_item`) e disparar `start_jml_event`, `invoke_edge_function`, `run_admin_sql`, `apply_migration`. Executor e aprovador na mesma entidade anulam a segregação.

**A6. Identidade sem unicidade.** `colaboradores` sem UNIQUE em `matricula`, `email`, `sam_account_name`, `cpf`; `perfil_atribuicoes` sem UNIQUE parcial (perfil, colaborador, ativo) — o código tem "safeguards" que desativam antes de inserir (sintoma). `iam_queue.colaborador_id` sem FK e recebe ids de `terceiros` (`terceiroLifecycle.ts:107`) — joins com colaboradores quebram para terceiros.

**A7. Qualidade de dados vira identidade.** `sync-csv-colab/index.ts:117-136`: linha sem `employID` ganha matrícula `SEM_MAT_<hash>`; matrícula duplicada ganha `_ROW_2` — erros do RH viram novas identidades (e potencialmente novas contas). Deveria ir para quarentena (a tabela `colab_quarentena` existe e **nunca é escrita**).

**A8. E-mail corporativo regenerado.** `buildColabData` (`sync-csv-colab:625-650`): se o e-mail do RH não é `@origoenergia.com.br`, gera um novo a partir do nome **a cada atualização** da linha; como o e-mail atual do próprio colaborador já está em `existingEmails`, a próxima tentativa (`first.middle`, `first.last2`…) troca o e-mail/sam de um colaborador existente. Domínios fixos no código: `@origoenergia.com.br`, `@ebessolar.local`, site `origoenergia.sharepoint.com:/sites/dataanalytics/RH_COLAB`.

**A9. Matching de identidade permissivo.** `process-iam-queue:625-700` e `reconcile-identities`: match por prefixo de e-mail (≥4 chars) e por "assinatura de nome" (primeiro|último token). Único no índice ≠ correto (homônimos, recontratados). O doc `iam-agent-orchestrated-mode.md` exige match único por `entra_id/email/sam/matricula` e cancelamento em ambiguidade; o código vai além disso. `resolveUserId` (`:58-100`) usa `value[0]` mesmo com múltiplos resultados.

**A10. `process-iam-queue` — bugs internos.**
- Dois blocos de delegação ao agente (`:855-905` e `:1481-1520`); o segundo retorna 202 sempre, então a exceção "remoção manual imediata" do primeiro e o filtro em `:1541-1545` são código morto. Cada chamada em modo agente grava uma linha de auditoria `processamento_delegado_agente` (spam: a UI chama após cada ação).
- `force=true` ignora `next_retry_at`; item que falha volta a `pending` e é re-lido no mesmo loop até `max_retries` (10 chamadas ao Graph na mesma invocação).
- 404/400 do Graph são retentados 10× (~85h de backoff) antes de falhar.
- `assign_app` (`:315-325`): sem `appRoleId`, escolhe `roles.find(… || r.isEnabled)` — pode cair num role administrativo.
- Retentativa e falha classificadas por `message.includes("AD local")`.

## 4. Achados médios

- **M1.** `eventos_jml.status` é cosmético: o frontend grava `executado` direto; CSV grava `pendente` e nada avança; `start-jml-event` grava `executando`. `mover` é gerado a qualquer mudança de campo (nome, área…), não só cargo. Enum tem `quarentena` sem uso.
- **M2.** Reativação via CSV (`sync-csv-colab:1069-1103`) reabilita conta mas não recria `perfil_atribuicoes` revogadas no desligamento → ferramenta mostra "sem acesso" enquanto o Entra tem tudo (C5).
- **M3.** `review_orphan_entra` é uma tarefa de revisão dentro da fila de provisionamento (polui KPIs); dedupe limitado a 2.000 itens (`process-iam-queue:1349-1362`).
- **M4.** `expire-access-exceptions:127` invoca `process-iam-queue` com service role, mas ela exige JWT de usuário → 401 silencioso. Mesmo padrão em `auto-recertification` → `send-review-email`.
- **M5.** Revisão externa: `revisoes.token` sem expiração (`get_revisao_by_token`, `save-external-review`); qualquer portador do link decide e revoga.
- **M6.** Modo simulação: `process-iam-queue` em `reconcile-create` **grava** (cancela itens, cria `disable_entra`/`enable_entra`, altera `entra_id`) mesmo em simulação.
- **M7.** Divergência CSV×Entra (`process-iam-queue:1213-1226`) enfileira `enable_entra` como `pending` só porque o CSV diz `ativo` — um erro de digitação no RH reabilita conta desligada (se o gate estiver off).
- **M8.** Terceiros: `desligarTerceiro` procura exceções por `colaborador_id = terceiro.id` (FK para colaboradores — nunca acha). Revalidação de 45 dias só gera alerta/e-mail; não bloqueia nada se ninguém responder.
- **M9.** `sync-user-access` grava acesso real como `iam_queue.status='success'` — o histórico de execução e o estado atual ficam indistinguíveis.
- **M10.** SoD: preventivo só no portal (`PortalSolicitacoesPage.tsx:196-220`, no browser). Atribuição direta (`usePerfilAssignment`), cargo→perfil e aprovações não checam SoD; nada no servidor.
- **M11.** Notificação ao gestor / e-mails são best-effort no browser (`sendNotificationEmail`), sem fila nem retry.
- **M12.** `handle_new_user` cria `profiles` sem papel; `must_change_password` default `true` sem fluxo claro para contas criadas fora de `admin-create-user`.

## 5. O que não faz sentido / pode ser removido ou simplificado

| Item | Evidência | Ação sugerida |
|------|-----------|---------------|
| Motor de regras (`regras`, `regra_condicoes`, `regra_resultados`, `execute-rules`) | Nenhuma tela chama a função; `MatrizPage` linka `/regras/:id/editar`, rota inexistente; mesmo executado só grava `perfil_atribuicoes` sem enfileirar nada | Remover (o RBAC real é `cargo_perfis`) ou terminar |
| `colab_snapshots` | Zero referências | Remover |
| `colab_quarentena` + status `quarentena` | Nunca escrita, só deletada | Remover ou implementar quarentena de fato (A7) |
| Guardrails de restore: `iam_restore_guardrails`, `suppress_restore_*`, `iam_change_backups`, `backup_*_2026070x`, `restoreOnly` em `sync-sharepoint-csv` | Ferramental do incidente de julho; triggers `suppress_restore_*` nem estão nas migrations | Remover após confirmar que o incidente está encerrado; manter backups fora do schema `public` |
| `sync-csv-colab` (upload manual) | Cópia divergente e mais perigosa (delete) | Uma única função com fonte (`sharepoint` \| `upload`) |
| Modo `reconcile-create` de `process-iam-queue` × `reconcile-identities` | Duas reconciliações | Uma só, com matching estrito |
| `provisionCargoAcessos` cliente × servidor | Divergentes | Um único RPC/edge function |
| Execução Graph dentro de `process-iam-queue` (modo `lovable_cloud`) | Se o agente é o executor oficial, são ~1.000 linhas de caminho alternativo | Decidir um executor. Se ficar o agente: `process-iam-queue` vira só orquestração/gate; se ficar o Lovable: agente só AD |
| `iam_execution_mode` + `modo_operacao` + `iam_approval_required` como strings em `parametros` | Editáveis por operador, sem tipagem | Tabela de configuração tipada, só admin |
| Status `pendente/executando/…` em `eventos_jml` | Nunca avançam | Tratar `eventos_jml` como log imutável (sem status) ou ligar ao ciclo de vida da fila |
| Domínios/sites hardcoded | `@origoenergia.com.br`, `@ebessolar.local`, `RH_COLAB` | `parametros` |
| `apply_reconcile_updates` sem checagem de papel | SECURITY DEFINER; se `authenticated` tiver EXECUTE, qualquer logado altera `entra_id`/`colaborador_id` | Restringir a `service_role` |

## 6. Arquitetura-alvo sugerida (para ter um IGA "funcional em todas as vertentes")

1. **Estado de acesso explícito.** Tabela `entitlements` (identidade × recurso × origem[cargo, perfil, exceção, solicitação, sync] × válido_até × status). `iam_queue` volta a ser só fila. Toda remoção passa por "acesso efetivo": remover recurso ⇔ nenhuma outra origem ativa o concede.
2. **JML no servidor, transacional.** RPCs `plpgsql` (ou uma edge function com uma transação via RPC) para `leaver`, `mover`, `joiner`, `pre_leaver`, `reativar`, chamadas tanto pela UI quanto pelo CSV e pelo MCP. Uma implementação, um teste.
3. **Máquina de estados na fila.** CHECK de status, trigger que valida transições, `claim_iam_queue_items`/`complete_iam_queue_item` usados por `iam-agent-api` e por `process-iam-queue`; `approved_by/approved_at` obrigatórios para sair de `waiting_approval`; `approved_by ≠ requested_by` (anti auto-aprovação no banco).
4. **Papéis com segregação.** `viewer` < `operador` (opera fila, não aprova nem edita parâmetros) < `aprovador` (por recurso/gestor) < `admin` (config) < `platform_admin` (DDL). `auditoria` append-only (sem UPDATE/DELETE), com ator real em todas as funções.
5. **Fonte RH com rede de proteção.** Threshold de leavers (ex.: > 5 % ou > N ⇒ modo dry-run + alerta), quarentena real para linhas inválidas/duplicadas, nunca DELETE, matching estrito (matrícula/entra_id/e-mail/sam exatos; ambiguidade ⇒ quarentena).
6. **Agente = executor.** Sem poder de aprovação; resolve identidade por `colaborador_id`/`entra_id`; implementa `update` AD, `revokeSignInSessions`, SharePoint; guardrail de `enable_entra` lendo `approved_by/approved_at` da fila.
7. **Agenda.** `pg_cron` (ou o agente) chamando com service role: ciclo diário do RH, expiração de exceções/terceiros, recertificação, reconciliação, limpeza. Todas as funções agendadas aceitam `requireRoleOrService`.
8. **Mover com desprovisionamento controlado.** Delta cargo antigo → novo gera `remove_*` em `waiting_approval` (ou com carência de N dias), respeitando acesso efetivo.

## 7. Plano proposto (ordem de ataque)

**Fase 0 — hotfixes (dias):** C1, C2, C3 (enfileirar remoções/disable na expiração de terceiro), C6 (guardrail e resolução de identidade no agente), A10 (blocos duplicados), M4, unificar `sync-csv-colab` no comportamento de `sync-sharepoint-csv` (sem DELETE) + threshold de leavers, parar o DELETE de fantasmas.
